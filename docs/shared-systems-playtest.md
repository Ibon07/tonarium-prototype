# 공유 시스템 로컬 동작 시험

Node 24와 이 작업 공간의 의존성이 필요합니다. 처음 한 번 `npm ci`를 실행한 뒤 다음 명령으로 시작합니다.

```sh
npm run dev:systems
```

기본 주소는 `http://127.0.0.1:5175/?systemPlaytest=1`입니다. 두 번째 창에는 `http://127.0.0.1:5175/?systemPlaytest=1&actor=bob`을 엽니다. 첫 번째 창은 alice, 두 번째는 bob으로 같은 시험 방에 참여합니다.

이 모드는 외부 kokosync·LiveKit 연결 없이 실제 `SystemService`와 중앙 시스템 패키지를 실행합니다. 오브젝트·이벤트·타이머·착석·상태 저장은 실제 공유 시스템 실행기이고, 공유 시스템 통신은 로컬 HTTP 어댑터로 처리합니다. 기본 아이템도 실제 아이템 생성·모델 표시 경로를 사용합니다. 일반 아이템의 체스 대국·그림 그리기 같은 원래 기능은 이 어댑터가 처리하지 않으므로 일반 게임 서버에서 `native` 모드로 시험합니다. 일반 게임의 kokosync 전송·VR 기기 입력·운영 배포도 별도 확인 대상입니다.

## 일반 Tonarium에서 확인

홈·세션 입장·아이템 메뉴와 실제 kokosync 동기화까지 확인하려면 일반 Tonarium 서버와 Vite를 실행합니다. 시작 방법은 README의 개발 항목을 따릅니다. 독립 시험의 `npm run dev:systems`와 일반 앱의 `npm run dev`는 서로 다른 실행 경로입니다.

이번 작업 공간의 전체 앱은 `http://127.0.0.1:5181/`에서 실행하며, API는 `3181`, 로컬 LiveKit은 `7880` 포트를 사용합니다. `.env`에서 포트와 `DATA_DIR=.local/tonarium-full`, `LIVEKIT_ROOM_PREFIX=tonarium-shared-systems-local`을 지정해 시험 화면·기존 데이터와 분리합니다. `.env`와 로컬 실행 파일은 Git에 제출하지 않습니다. LiveKit의 로컬 개발 실행은 [공식 안내](https://docs.livekit.io/transport/self-hosting/local/)를 따릅니다.

일반 화면에서 이름 입력 → 세션 입장 → 3D 전환 후 동기화가 연결됐는지 확인합니다. 홈이나 게임 내부 메뉴에서 **월드 → 아이템 → 공유 시스템** 순서로 배치된 항목을 눌러 목록을 엽니다. 이 목록은 세션 밖에서도 사용할 수 있습니다. 일반 세션 화면의 테스트용 바로가기와 코드 예제 실행 패널은 제거했습니다. 버튼·타이머·의자 예제의 수동 시험은 위의 독립 시험 화면에서 진행합니다.

시스템 파일을 추가하는 실제 흐름은 **새 버전 파일과 변경 이력을 PR로 제출 → 검사 → 병합 → 서버 재배포 → 목록 확인 → 맵 코드에 ID·바인딩 추가**입니다. 로컬에서는 현재 체크아웃의 `shared-systems/`를 서버가 시작할 때 분리된 저장소에 등록하므로 먼저 같은 흐름의 실행 결과를 확인할 수 있습니다. 앱의 목록에서 파일을 직접 업로드하는 방식은 사용하지 않습니다.

## 확인 순서

1. 시작 버튼이나 장면의 체스판을 누르면 같은 타이머가 시작되는지 확인합니다. 타이머의 표시 대상은 실제 메모 아이템이며, 두 창의 메모와 오른쪽 남은 시간에 같은 값이 표시되어야 합니다. 이 체스판은 버튼 시스템의 대상이므로 체스 대국 동작은 실행하지 않습니다.
2. 일시정지 후 잠시 기다렸다 다시 시작하면, 정지한 동안 시간이 줄지 않고 남은 시간부터 이어지는지 확인합니다.
3. 초기화 버튼을 누르면 타이머가 설정한 전체 시간으로 돌아오는지 확인합니다.
4. 타이머가 완료되면 두 창 모두 남은 시간이 `00:00`, 상태가 완료로 표시되고 타이머가 멈추는지 확인합니다. 초기화하면 다시 전체 시간으로 돌아와야 합니다.
5. 장면의 의자를 누르면 클릭한 사용자가 앉습니다. 오른쪽의 참가자 선택과 앉히기 버튼으로는 다른 접속자를 선택할 수 있습니다. 이미 사용 중인 의자에 다른 사용자가 앉으려 하면 거부되는지 확인합니다.
6. 스페이스바를 누르면 현재 창의 참가자가 일어섭니다. 참가자 선택은 이 단축키에 영향을 주지 않습니다. 일어서기 후 의자가 비고, 다른 사용자가 앉을 수 있는지 확인합니다. 기존 일어서기 버튼도 유지합니다.
7. 사용 중인 창을 닫으면 최대 15초 안에 해당 사용자의 착석이 해제되는지 확인합니다. 같은 사용자 슬롯의 다른 창이 열려 있으면 착석은 유지됩니다.
8. 실행기를 종료했다 다시 켰을 때 저장된 오브젝트·시스템 상태를 이어받는지 확인합니다. 돌아오지 않은 사용자의 착석은 정리됩니다.

상태·진단에 오류가 표시되면 내용을 확인합니다. 일반 게임의 입력은 응답을 기다려 순서대로 전송합니다. 타이머 갱신과 겹쳐 서버가 해당 입력의 revision 충돌을 명시적으로 반환하면 최신 상태로 최대 8회 재시도합니다. 응답이 없거나 연결이 끊긴 입력은 중복 실행을 막기 위해 자동 재전송하지 않습니다. 다시 연결한 뒤 상태를 먼저 확인합니다.

## 데이터와 종료

시험 데이터는 저장소의 `.local/system-playtest/`에만 저장합니다. 기존 `data/`와 운영 볼륨을 사용하지 않습니다. 같은 폴더를 유지하면 이전 시험 상태가 이어집니다. 타이머 초기화는 시험 화면에서 제공하는 초기화 버튼을 사용합니다.

종료하려면 실행한 터미널에서 `Ctrl+C`를 누릅니다. 로컬 API와 Vite가 함께 종료됩니다. 포트가 이미 사용 중이면 자동으로 다른 포트를 고르지 않고 시작을 중단합니다.

필요할 때 `SYSTEM_PLAYTEST_API_PORT`와 `SYSTEM_PLAYTEST_WEB_PORT`로 API·웹 포트를 바꿀 수 있습니다. 기본값은 각각 3002, 5175입니다. 주소는 항상 루프백으로만 열리며, 외부 Origin의 쓰기 요청과 프로덕션 모드 실행을 거부합니다.

자동 회귀 시험은 다음과 같습니다.

```sh
npm run test:systems
npm run test:systems-playtest
```

로컬 어댑터의 시험은 실제 loopback HTTP로 두 사용자·버튼→타이머·착석 경쟁·퇴장 정리·오래된 입력·외부 요청 차단을 확인합니다. 브라우저의 실제 모델 표시와 앉기 애니메이션은 위 수동 확인으로 구분합니다.

## 실제 서버 통신 자동 시험

다음 시험은 HTTP 시험 어댑터 대신 일반 `server/index.ts`, 실제 참가 자격 발급, 암호화된 kokosync 전송을 사용합니다. 외부 kokosync 중계에 접속할 수 있어야 합니다. LiveKit과 마이크는 사용하지 않습니다. 기본 실행에서는 생략되므로 명시적으로 활성화합니다.

```sh
KOKOSYNC_INTEGRATION=1 npm run test:systems:integration
```

PowerShell에서는 `$env:KOKOSYNC_INTEGRATION='1'`을 설정한 뒤 `npm run test:systems:integration`을 실행합니다. 시험이 임시 데이터 폴더·빈 로컬 포트·고유 방 이름으로 서버를 만들고 종료하므로 실행 중인 로컬 게임과 운영 데이터는 사용하지 않습니다.

등록 시스템 3개와 원본 파일의 SHA-256, 등록 맵 불러오기, 실제 메모·체스 아이템 생성, 진행 후 입장한 사용자의 전체 상태, 두 사용자의 타이머·메모 갱신, 의자 점유 거부, 데이터 연결을 다시 맺었을 때 상태 복원, 중복·오래된 명령, 타이머 갱신과 의도적으로 충돌시킨 입력의 실제 클라이언트 대기열 복구, 연속 시작·정지·초기화, 퇴장 후 의자 해제, 다른 방과의 분리, 실제 10초 타이머 완료와 완료 후 입장을 확인합니다. 이 자동 시험의 브라우저 화면·WebRTC·음성·VR 검증은 별도입니다.

## 중앙 라이브러리 확인

화면의 **등록된 공유 시스템 보기**를 누르거나 `http://127.0.0.1:5175/?systemLibrary=1`을 열면 중앙에 등록된 항목을 볼 수 있습니다. 기본 예제는 `button`, `timer`, `chair` 세 가지입니다. 검색으로 항목을 찾고 설명·연결 대상·설정·상태·입출력·공개 버전·원본·코드 연결 예제를 확인합니다. 로컬 시험의 목록은 실제 `SystemService`가 제공하므로 향후 새 패키지를 추가한 뒤 시험 서버를 다시 시작하고 목록을 새로 불러와 확인할 수 있습니다.

목록 위에는 **공유 시스템 사용법**과 **새 시스템 등록 가이드**가 접힌 상태로 표시됩니다. 제목을 눌러 맵 작성·연결 예제와 양식 생성·검사·PR 제출·배포 절차를 화면 안에서 읽고, 다시 눌러 접습니다. 자세한 등록 계약은 [시스템 등록 가이드](shared-systems-registration.md)를 참고합니다. 원시 카탈로그는 같은 서버의 `/api/shared-systems`에서도 확인할 수 있습니다. 시험 데이터 폴더는 공개 원본을 보존하므로, 이전 시험에서 등록한 추가 버전이 있다면 세 기본 예제 외의 기록도 목록에 남을 수 있습니다.

라이브러리의 **기존 아이템을 ID로 배치하기**를 펼치면 지원하는 기본 아이템 12종의 ID·이름을 조회하고 검색할 수 있습니다. 같은 항목에서 기본 배치와 타이머 표시판 연결 코드를 확인합니다. 일반 게임의 기존 아이템 메뉴에도 선택한 항목의 `itemId`가 표시되지만, 공유 시스템 맵에서는 라이브러리의 기본 아이템 목록에 있는 ID만 사용합니다. 스토어 상품과 미디어 아이템은 이 목록과 공유 시스템 맵 배치에서 제외합니다. 기본 아이템 목록은 중앙 공유 시스템 세 패키지의 목록과 구분됩니다.

## 실제 아이템 ID 연결 예제

현재 `shared/system-demo.ts`에는 다음 두 배치가 포함되어 있습니다. 둘 다 기존 아이템의 모델을 사용하는 `system` 모드입니다.

| 맵 배치 ID | 메뉴 아이템 ID | 연결된 공유 시스템 |
| --- | --- | --- |
| `timer-text` | `note` | `countdown` 타이머의 `display`. 메모에 남은 시간을 표시합니다. |
| `menu-chess-button` | `chess` | `menu-start` 버튼의 `target`. 체스판 클릭 → `pressed` → 기존 타이머의 `start`로 연결합니다. |

맵 작성 코드는 다음 형태입니다. 기존 예제의 일부이며 `countdown` 배치와 시작·정지·초기화 연결은 같은 맵에 작성되어 있습니다.

```ts
.item({
  id: 'timer-text', itemId: 'note', itemMode: 'system',
  capabilities: ['text'], position: [-1, 0, -3], text: '00:10',
})
.item({
  id: 'menu-chess-button', itemId: 'chess', itemMode: 'system',
  capabilities: ['interact'], position: [1.5, 0, 0],
})
.system({
  instanceId: 'countdown', systemId: 'timer',
  bindings: { display: ['timer-text'] }, config: { duration: 10 },
})
.system({
  instanceId: 'menu-start', systemId: 'button',
  bindings: { target: ['menu-chess-button'] }, config: {},
})
.connect({ from: 'menu-start', output: 'pressed', to: 'countdown', input: 'start' })
```

`bindings`에는 `note`·`chess` 대신 맵 배치 ID를 넣습니다. `system` 모드에서는 원래 아이템의 게임·편집·운반·수거 입력을 막고 공유 시스템의 입력만 처리합니다. 기본값인 `native` 모드로 배치하면 기존 아이템 기능을 유지하지만 공유 시스템 대상으로는 연결하지 않습니다. 아이템 배치 높이는 바닥인 `0`입니다. `.item(...)`은 기존 아이템 렌더러에 자동 연결되므로 같은 배치에 모델을 따로 추가하지 않습니다.

일반 서버에서 `native` 배치를 시험할 때는 게임·메모·그림 상태와 사용자가 옮긴 위치가 맵 재호출·재시작 후 유지되는지 확인합니다. 원본 배치 좌표나 회전을 수정하면 새 위치를 적용합니다. 사용자가 수거한 배치는 일반 시스템 처리마다 다시 만들지 않지만 명시적인 맵 불러오기나 서버가 처음 맵 상태를 복구할 때 다시 생성될 수 있습니다. 기존 아이템이 남아 있으면 원래 게임 상태를 유지합니다. 맵 전환 시 사용자가 별도로 꺼낸 아이템이 삭제되지 않는지도 확인합니다. 자세한 계약은 [아이템 ID와 제어 모드](shared-systems.md#아이템-메뉴의-아이템을-id로-배치)를 참고합니다.

## 기존 모델을 연결하는 코드

`SystemObject`는 안에 넣은 기존 모델을 유지하면서 맵의 안정적인 오브젝트 ID에 연결합니다. 부모에 회전·배율이 있어도 맵 좌표를 변환하고, 해제할 때 기존 위치·회전·상호작용을 복원합니다. 원래 모델의 geometry와 material은 이 연결 코드가 삭제하지 않습니다.

```tsx
<SystemObject objectId="chair-object">
  <MyChairModel />
</SystemObject>

<SystemObject objectId="custom-label">
  {text => <Label text={text} position={[0, 0, 0]} height={0.3} />}
</SystemObject>
```

실제 연결 예제는 `client/src/systems/SystemObjects3D.tsx`와 `demo-models.tsx`입니다. 이 예제의 모델은 맵 표현 코드이며 중앙 시스템 패키지에 들어 있지 않습니다. 의자의 `seatOffset`은 앉을 위치의 기준점입니다. 앉기 전환은 캐릭터 전체 위치와 다리 각도만 조정하며, 손·머리·상체의 기존 감정 표현이나 시선·기울기 동작을 고정하지 않습니다. 일어서면 전체 위치 보정과 다리 회전만 원래대로 되돌립니다.

위 `SystemObject` 방식은 `.object(...)`로 정의한 별도 모델을 연결하는 경우입니다. `custom-label`도 같은 맵의 오브젝트로 정의해야 합니다. 실제 아이템 ID 배치는 앞의 `.item(...)` 방식을 사용합니다.

앉은 자세는 초기 구현보다 몸을 0.20m 높이고, 다리를 서 있을 때 기준으로 앞으로 45도 회전합니다. 몸과 카메라의 높이 보정은 `seatedBodyOffset`을 공유하며, 일어서면 높이·다리 회전이 모두 원래 자세로 복원됩니다.

앉은 상태에서 `손 흔들기 (이 창)`을 누르면 선택한 참가자의 손 동작이 다리 자세와 함께 유지되는지 확인할 수 있습니다. 이 버튼은 해당 창의 표시 검사용이며 다른 창으로 감정 표현을 배송하지 않습니다.

스페이스바는 앉아 있을 때만 일어서기 입력으로 사용하고, 서 있을 때는 일반 게임의 점프 입력을 유지합니다. 입력란·텍스트 영역·참가자 선택 메뉴에서는 가로채지 않습니다. 길게 눌러도 일어서기는 한 번만 요청하며, 키를 뗄 때까지 반복 입력이 점프로 이어지지 않습니다.

## 확인한 범위

2026-10-26 Windows 로컬 서버와 독립 시험 화면의 Alice/Bob 두 창에서 3D 버튼 클릭, 두 창의 타이머 상태 일치, 일시정지·이어가기, 착석 표시·중복 점유 거부·일어서기 복귀를 확인했습니다. 시험용 아바타는 같은 GLB에 채워진 SVG 텍스처를 사용해 자세를 쉽게 확인합니다.

같은 날 일반 Tonarium 전체 앱의 `?as=sync-qa-alice`·`?as=sync-qa-bob` 두 창도 실제 WebRTC kokosync 연결로 확인했습니다. 예제 맵·실제 체스판·메모를 불러오고 연속 시작·정지·초기화와 착석을 처리했습니다. 두 창의 타이머를 `00:04`에서 정지한 뒤 한 사용자가 나갔다 다시 입장해도 메모와 현재 시스템 상태가 같고 다른 사용자의 착석이 유지됐습니다. 브라우저 오류 로그는 없었으며 Three.Clock 사용 중단 예정 경고는 남아 있습니다. 별도 자동 시험은 WebSocket 전송으로 전체 서버·늦은 입장·데이터 재연결·명령 충돌을 확인했습니다. 음성 대화와 VR 장치 입력, 운영 서버 배포는 시험하지 않았습니다.
