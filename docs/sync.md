# セッションの同期（kokosync）

セッション内のデータは kokosync、フレンド・DM・ホームは既存の WebSocket、音声・映像は LiveKit を使う。アプリ側の `send()` とメッセージ型は維持している。

## 経路と担当

| 経路 | 流すもの | 実装 |
| --- | --- | --- |
| `/ws` | 接続、参加・退出、フレンド、DM、グループ、招待、セッション一覧、プロフィール、同期の接続情報 | `client/src/net/ws.ts`、`server/index.ts` |
| kokosync | チャット、アイテムとキャンバス差分、位置、presence、ワールド、ゲーム、通知、初回同期 | `client/src/net/session.ts`、`server/rooms.ts` |
| LiveKit | 通話、画面共有、カメラ、視点のライブ配信 | `client/src/net/livekit.ts` |

画面共有のラクガキは LiveKit の reliable データパケット（`share-annotations-v1`）で同期する。共有トラック SID をキーに映像内の 0〜1 座標で線分とカーソルを送る。線分は共有者を経由して配信する。共有者が履歴を保持し、途中参加者の要求に小分けで応答する。履歴とリアルタイムの線分は ID で重複排除して合流する。カーソルはモード終了・表示終了・参加者退出で除去し、共有終了・通話切断で履歴と再要求タイマーを破棄する。サーバー保存は行わない。検証用の同期・座標変換テストは `npm run test:share`。

接続先の既定値は `https://45.77.130.146`。ブラウザは WebRTC、Tonarium サーバーは WebSocket で同じ kokosync ルームに参加する。UDP が使えないブラウザは、8秒の接続試行後に同一オリジンの `/sync/ws` を経由する WebSocket に切り替える。この互換接続では TCP の順序待ちがあるので、WebRTC と同じ低遅延は保証できない。

Tonarium サーバーが参加を判定し、状態更新を処理する。新しいクライアント同士の位置と、下記のイベント本文はkokosync SDKが相手ごとにWebRTC直結を試し、接続できなければkokosync中継で届ける。直結先の上限は1クライアントあたり5人。アプリサーバーには初回同期用の位置を別途送り、同じ位置を新しいクライアントへ再配信しない。旧クライアントへの位置配信は従来のサーバー経由を維持する。権限判定・イベントの適用順・初回同期・状態保持はアプリサーバーが担当する。

直結は共通のWebRTCアダプターとネットワーク条件が成立した組だけが使う。Go・C#など直結アダプターのないクライアントは中継になる。シグナリング用にWebSocketを使っていても、ブラウザにWebRTCがあれば相手との直結は可能。ICEサーバーはSDK既定の空設定であり、異なるNAT間の接続を保証しない。SDKの直結表示はkokosync中継を迂回する接続を示し、将来TURNを指定した場合はTURN中継を含み得る。

## 互換性バージョン

通信の約束事には、画面の版（CLIENT_VERSION）とは別に互換性バージョン（`shared/protocol.ts` の `COMPAT_VERSION`）を持つ。クライアントは `/ws` の `hello` で申告し、サーバーは一致しない接続（申告が無い旧クライアントを含む）を `incompatible` を送って断つ。断たれた Web クライアントは再接続せず、全面に「バージョンが変わりました」と出して再読み込みを促す。

- 上げるタイミング: メッセージ種別の追加・削除、意味や暗号・順序の前提の変更など、約束事を壊す変更を入れたとき。画面だけの変更では上げない（そちらは CLIENT_VERSION が検出する）

## 参加と初回同期

`sessionCreate` の成功時は作成者のソケットにだけ `sessionCreated`（新規セッション ID）を返す。`requestId` 付きの作成失敗・参加・退出には `sessionResult` を返し、失敗時はエラーだけでセッション ID を含めない。Web クライアントは作成応答から共通の参加処理を呼び、移動時は退出と通話切断の完了を待つ。`sessions` は一覧更新専用で、受け取っても参加状態を変えない。

1. `/ws` の `join` で、既存の公開範囲チェックを受ける。
2. `prepareSync` に対して、その接続専用の参加情報 `syncConfig` を返す。退出・切断・再発行まで有効。サーバー起動ごとの名前空間で、他の Tonarium インスタンスと部屋が混ざらない。
3. ブラウザは `/sync/offer` に参加資格を渡して WebRTC を確立する。kokosync の Basic 認証情報は Tonarium サーバーだけが保持する。
4. `sync` に対してアプリが `SessionSnapshot` を送る。チャット、キャンバスを含むアイテム、位置、presence、ワールド、ゲーム、サーバー時刻を一括して復元する。
5. 復元後に mode、音声状態、位置、閲覧状態を送り直し、接続中に待っていた操作を送る。

`prepareSync` では `peerPositions: true` を通知する。対応する中継サーバーに限り、専用の位置共有鍵を返す。認可された相手のpeer・ユーザーID・位置共有鍵は、既存の暗号化された確実配送で通知する。SDKの直結候補はこの一覧に限定する。非対応サーバーや旧クライアントには従来経路へ戻る。

状態の正は既存の Tonarium サーバーにある。kokosync の state/checkpoint は使わず、初回同期はアプリが引き受ける。スナップショットを作った後の確実配送は、受信者ごとの同じ送信列に並ぶ。大きいスナップショットの受信・適用が終わる前に、後続の差分を適用しない。

## 確実配送のP2P化

対象は全体・アナウンスのチャット（添付画像を含む）、キャンバスの描き始め・点の追加・全消去、サイコロのアイテム更新。`prepareSync.peerDelivery` と接続先の対応能力を確認し、旧クライアント・未対応のサーバーには従来経路を使う。近距離チャット、サイコロの遅延後のログと秘密の結果、アイテムの作成・移動・削除、ゲームなどはサーバー経由のまま。

1. 送信者がイベントIDと今回だけのAES鍵を作り、更新本文を暗号化して認可済みpeerへ `sendTo` で先に配る。受信者はこの時点では適用しない。
2. 操作・イベントID・鍵・本文のハッシュを、既存の暗号化された操作経路でサーバーへ送る。サーバーは従来どおり権限と操作を検証し、状態へ反映する。サイコロはクライアントが結果を生成し、サーバーが面数・個数・値域・連投間隔を検証する。
3. サーバーが生成した正規の更新とハッシュが一致した場合、対象者にだけ鍵とハッシュを含む小さい確定通知を送る。受信者は本文を復号・照合し、サーバーが確定した順序で適用する。入力の修正などで一致しなければ正規の更新全文を従来経路で送る。
4. 本文が250ms待ってもない場合、受信者はサーバーへ補完を要求する。サーバーはその受信者に確定通知を送った本文だけを返す。10秒以内に復元できない場合や受信待ちが256件・64 MiBを超えた場合は、再接続してスナップショットを取り直す。

本文は状態の正として採用する前に必ずサーバーの確定通知と照合する。複数送信者の操作も、削除や全消去も同じ順序になるため、P2Pの到着順で状態が分岐しない。P2P対応のキャンバスは送り主も確定通知の順で反映し、同時の全消去で送り主だけ描画が残る状態を防ぐ。秘密のサイコロはP2P本文にも結果を入れない。確定通知・鍵・補完用本文は受信者専用の暗号化を維持する。

P2P用の本文キャッシュと送信待ちは各32 MiB・128件、キャッシュの有効期限は60秒。サーバーの補完キャッシュは受信者ごとに32 MiB・128件・有効期限60秒で、退出時に破棄する。イベントIDの再実行防止はセッション内の直近4096件。SDKの送信枠を使い切らないよう同時送信は2件で、小さい本文と16 KiB超の本文を別トピックに分ける。現在の接続先の1値上限は4 MiBで、超える候補は従来のBlob経路へ戻す。既存の初回同期・大きいBlob転送の上限は次節のとおり。

この段階では操作の送信自体はサーバーにも必要で、サーバーの処理・保存をなくしてはいない。受信側への本文配送をP2P化し、確定通知と復元で整合性を保つ構成。汎用の本文配送・復元は `shared/session-events.ts`、適用する操作の種類は同ファイルの `proposeEvent` にある。

## 大きいデータと位置更新

- 本文は MessagePack。省略可能フィールドの `undefined` はエンコード時に除く。
- 48 KiB を超える暗号化パケットは、kokosync の宛先付き Blob 転送を使う。フロー制御とハッシュ検証は SDK が行う。受信完了時に一括適用する。
- アプリの1パケット上限は暗号化前で約32 MiB、受信者ごとの送信待ちは64 MiB。超過・切断を黙って無視せず、再同期と画面への通知を行う。
- サーバーからの大きい Blob はルームごとに直列化し、kokosync の同時転送枠を使い切らないようにする。遅い受信者が他の大きい転送を待たせることはある。
- 位置は最大約30fpsで `latest` に流す。確実配送や Blob の送信列とは別に処理し、古い値を捨てる。描画側の補間は従来どおり。
- アイテムの移動は中身（キャンバスの線など）を含めず、位置だけの `itemMove` を配る。サーバー側でアイテムごとに 80ms へ間引き、位置が変わっていないものは送らない（止まったときの最後の位置は必ず届ける）。作成・内容の更新・削除は従来どおりアイテム全体を配る。
- 位置の宛先は認可された相手とアプリサーバーに限定する。P2Pと中継で同じ位置共有鍵・連番を使い、切り替えによる重複を除く。退出した相手は候補・宛先・受信許可の一覧から外す。位置は損失許容のため、切り替え時の欠落は次の更新で補う。
- 動画ファイルのアップロードは従来の `/media`、リアルタイム映像は LiveKit を維持する。動画をこの Blob 経路に載せ替えたわけではない。
- 現在の kokosync の上限は1ルーム32 peer。この構成ではアプリサーバーが1枠使うので、参加者は最大31接続。1ユーザーが複数タブで参加すると、その分の枠を使う。空室の情報も中継サーバーが保持するため、開発で起動を繰り返す場合は中継側の総ルーム数上限にも注意する。

## 宛先と参加資格

kokosync の通常メッセージはルーム全員へ届くため、Tonarium は受信者ごとの AES-GCM 鍵で本文を暗号化する。声の範囲のチャット、シークレットのサイコロ、個人宛て通知は対象者だけに復号できる。サーバーは送信者の peer とホーム接続を照合し、クライアントの本文に書かれたユーザー ID を信用しない。方向・資格・通し番号も認証対象にして、別の方向への使い回しや再送を拒否する。

位置共有鍵は操作・個別メッセージ用の鍵と分ける。位置を受け取る側は、認可一覧のpeerとSDKが確認した送信者を照合する。位置データからユーザーIDを採用しない。位置共有鍵でチャットなどの操作を送信することはできない。

退出、ホーム接続の切断、参加情報の再発行で古い資格を無効にする。WebRTC の中継接続自体が残る場合も、その資格による操作は受け付けず、新しい本文は送らない。ホームの名前・ユーザー ID に関する認証強度は既存プロトタイプのまま。実運用のアカウント認証を追加したものではない。

## 再接続と診断

- ホーム接続が切れたらデータ接続も破棄し、`join` からやり直す。
- ホームの `/ws` はサーバーが25秒ごとにWebSocket制御フレームのpingを送る。ブラウザの自動pongでアイドル切断を防ぎ、次の確認時点まで応答がなければ切断して再接続させる。JavaScriptのタイマーに応答を任せないため、バックグラウンドタブのタイマー制限の影響を受けにくい。コンソールの `[home-ws] closed` には切断コード・理由・接続秒数を出す。
- kokosync の切断やタイムアウト時は待ち時間を増やして再接続し、最新のスナップショットをもらう。送信済みか不明な操作を自動再実行しない。未確定の操作があるときは確認を促す。
- LiveKit が切れてもデータ同期は続く。画面には同期と通話の状態を別々に出す。
- `useStore.getState()` の `sync`、`syncTransport`、`syncRtt`、`syncStats`、`syncError` で状態を取得できる。`syncStats` は SDK の queuedBytes / sentBytes / receivedBytes / dropped 等。5秒ごとに更新する RTT はブラウザから kokosync 中継までの往復で、操作が全員へ反映される時間とは異なる。
- `syncRoutes` は相手ごとのユーザーID・直結/中継・理由・直結RTT・経路別の送受信数を返す。画面に「位置同期 P2P ○人・中継 ○人」を表示し、ホバーで詳細を確認できる。経路変更は即時、カウンターとRTTは5秒ごとに更新する。送信数は送出したコピー数であり、到達保証ではない。
- ブラウザのコンソールには約1秒ごとに `[kokosync:peers]` グループを出す。位置の毎秒送受信数に加え、`deliveryStats()` の相手・経路・通信種別ごとのバイト数、メッセージ数、再送、待機量、未確認数、RTTを表示する。見出しの `data P2P 送信/受信` と `relay 送信/受信` は確実配送の累計件数。毎秒値は実際の経過時間で割ったフレーム数で、損失率ではない。SDKが保持する値を読むため追加の通信は発生せず、切断時に出力を停止する。RTTの更新頻度はSDKの測定周期に従う。

## 設定と検証

接続先とプロトタイプ用の Basic 認証情報は `server/kokosync-config.ts` に固定してある。既定の接続先に対して認証環境変数が両方とも空なら、この値を使う。`.env` / デプロイ環境の `KOKOSYNC_URL` と `KOKOSYNC_USERNAME`・`KOKOSYNC_PASSWORD` で上書きできる。別の接続先には同梱の認証情報を送らない。ローカルでは `KOKOSYNC_CREDENTIALS_FILE` に `Username:` / `Password:` 行のあるファイルを指定できる。`VITE_` を付けない。ブラウザは HTTPS または localhost で開く。

```sh
npm run typecheck
npm run build
npm run test:sync
npm run test:chess
```

接続先を実際に使う統合テストは、環境変数 `KOKOSYNC_INTEGRATION=1` を設定して `npm run test:sync:integration`。一時データディレクトリの Tonarium を起動し、独立したルームで初回同期、大きい添付、転送を止めた間の位置更新、キャンバス差分、個別配送、再接続、重複の拒否、別セッションとの分離、退出後の資格無効化、フレンド・DMを確認する。実接続するため通常の単体テストとは分けている。多数同時接続時の性能試験は別途必要。

2026-10-21に、ローカルのTonariumと既定のkokosync接続先を使い、同じPCのブラウザ5画面で検証した。全員から残り4人への直結が成立し、各組で位置の送受信カウンターが増えることを確認した。ブラウザ4画面とWebRTCを持たないNodeクライアント1つの構成でも、ブラウザ同士は直結、Nodeとの間は中継に分かれ、位置が届いた。異なるNATや回線をまたぐ直結成功率、継続的な負荷、最大人数の性能を保証する検証ではない。

確実配送の追加後も5画面で確認し、チャット・サイコロ・キャンバス操作の3件について、送り主はP2P送信12件、残り4人はそれぞれP2P受信3件・中継0件を記録した。統合テストでは5接続で240 KBの添付、描画と全消去の競合、イベントの再送、秘密のサイコロ、P2P本文欠落時の補完、途中参加による状態復元を確認している。

SDK は `vendor/kokosync/` に同梱してあり、別リポジトリのチェックアウトを必要としない。出典と変更点は同ディレクトリの README を参照。
