# 変更履歴の登録と集約

修正・文書更新・保守を含む全タスクで、`changelog/` 直下に作業別 JSON ファイルを一つ新規追加する。共通の `shared/changelog.ts` への手動追記は不要。このファイルは移行前の履歴として保持する。今回の方式移行に限り、依頼に従って共通履歴にも一項目を追記している。

## 配置と記載形式

名前は `YYYY-MM-DD-<識別子>.json`。識別子には英小文字・数字を使い、単語をハイフンでつなぐ。例は `changelog/2026-10-25-task-123-history-files.json`。同日に複数の作業を行う場合も別の識別子にする。タスク番号などを含めると衝突を避けやすい。

```json
{
  "date": "2026-10-25",
  "title": "作業別の変更履歴ファイルを自動集約",
  "items": ["実際に行った変更を利用者に分かる言葉で記載します。"],
  "tag": "開発・保守"
}
```

一ファイル一項目。`date` はファイル名と一致する実在日付、`title` は空でない文字列、`items` は空でない文字列を一つ以上含む配列。`tag` は省略可能で、指定時は空でない文字列。これ以外の項目、サブディレクトリ、JSON 以外のファイルは認めない。履歴をコードとして実行しない。

追加した JSON は実装と一緒にコミット対象へ含める。ローカルの完了チェックは未追跡ファイルも読むため、成功しても `git status --short` で追加漏れがないか確認する。

## 識別と表示順

作業別項目の ID は拡張子を除いたファイル名であり、登録済みファイルは編集・削除・改名しない。訂正も新しい作業別ファイルとして追加する。同じ内容（日付・見出し・本文・タグ）の作業別ファイルを複数置くと検証エラーになる。

表示は日付の降順。同じ日付の作業別項目は ID の文字列降順、続いて移行前の履歴を元の順序で表示する。移行前の履歴にも内部 ID を付け、既存項目は全件保持する。作業別ファイルと共通履歴に同じ内容がある移行項目は、共通履歴の一件だけを表示する。

## 集約のタイミング

Web は Vite が `shared/changelog.ts` を取り込む際に、共通履歴と作業別 JSON をメモリ上で集約する。`npm run build`、Dockerfile の `npx vite build`、開発サーバーに共通の Vite プラグインを使う。Windows ネイティブ版はビルド中の `native/export-changelog.ts` で同じ集約処理を使う。生成結果を入力ファイルへ書き戻さず、デプロイ先の永続データにも追記しないため、同じ入力で再ビルド・再デプロイしても項目は増えない。履歴ファイルは集約後もリポジトリに残す。

検索・日付単位の既読管理は従来どおり。同日に追加した履歴は、その日を既読にした利用者には未読の赤い点を出さない。

## 完了チェック

タスク完了前に `npm run check:completion` を実行する。`npm run check:changelog` は比較元に存在しない作業別ファイルが一つ以上あること、全作業別ファイルの形式・内容重複、既存履歴の保持を確認する。コミット済み・ステージ済み・未ステージ・未追跡の現在のファイルを対象とする。共通履歴の追記だけでは通過しない。記載内容と実際の差分の一致はレビューで確認する。

比較元は既定で `git merge-base HEAD origin/main`。タスク開始時のコミットを明示する場合は `CHANGELOG_BASE` を設定するか、`npm run check:changelog -- --base <比較元コミット>` を使う。比較元を取得できない場合も失敗する。PR の Web checks も同じ検証を使う。回帰テストは `npm run test:changelog`。
