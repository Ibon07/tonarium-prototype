# セッション同期のP2P化方針

2026-10-21に合意した設計と、その後の実装記録。kokosync SDKの取り込みと、本文のP2P配送・サーバーの確定通知を組み合わせる第一段階を実装済み。現在の動作と対象の範囲は [sync.md](sync.md) を参照。

## 目標と分担

セッション内の更新を汎用の通信APIに載せ、接続できる相手とはP2P、接続できない相手とはkokosync中継で交換する。アプリは配送経路を選ばず、更新の意味と適用方法を定義する。現在はサーバーで全体順序を確定し、整合性を維持したまま本文をP2P配送する方式を採用した。以下の所有権・競合解決の案は、サーバーの順序確定を外す将来段階の設計であり、実装済みの動作ではない。

- kokosync：参加peerの識別、経路選択、配送、再送、順序、重複排除、分割、流量制御、通信統計。
- Tonarium：参加権限、宛先の認可、暗号化、状態の適用、競合解決、初回同期、保存。
- 初期段階では参加管理・初回同期・保存をTonariumサーバーに残す。フレンド・DM・LiveKitは現状を維持する。

## kokosyncに必要な拡張

| 通信の種類 | 対象 | 配送の性質 |
| --- | --- | --- |
| 最新値 | 位置、向き、カーソル | 新しい値を優先し、古い値を捨てる |
| 確実配送 | チャット、操作、キャンバス差分 | 宛先ごとの到着確認、再送、重複排除、送信者・トピック単位の順序 |
| 大容量 | スナップショット、画像、ファイル | 分割、検証、キャンセル、流量制御。小さい操作と最新値を待たせない |

現在のP2Pは小さい `latest` / `live` のみ。確実配送と大容量転送にもP2P経路を追加する。JS・C#・Goで共通の配送契約を持ち、直結アダプターを持たない実装は同じAPIで中継する。

既存の `message` が持つコアのログ連番や `checkpoint` / `catchup` の意味は変更しない。peer間の確実配送はそれらと区別するAPI・プロトコルとして設計する。API名はkokosync側で確定する。

P2Pと中継の切り替えでは、同じ論理メッセージIDを引き継ぐ。送信先に届いたか不明なデータは再送し、受信側は二重適用しない。バッファ・再送・待ち時間には上限を設け、回復できない場合はアプリへ失敗を返す。無期限の再送や、切断をまたぐ厳密な一度限りの実行は保証しない。

到着確認は受信側の配送層が受け取ったことを表し、アプリでの適用・サーバーへの永続保存とは区別する。保存完了を必要とする操作にはTonarium側の応答を設ける。

小さい操作と大容量転送には独立した待ち行列・送信枠を設ける。回線容量は共有するため、最低限の優先送信枠とバックプレッシャーも必要。別の待ち行列に分けるだけでは低遅延を保証できない。

統計は相手・経路・通信の種類ごとに取得できるようにする。RTT、送受信フレーム数・バイト数、再送数、待ち行列、未確認数、経路変更理由を対象にし、取得できない項目は未計測として扱う。

## Tonariumの状態同期

アプリのイベントには一意なID、送信者の接続世代、連番、対象、操作種別を持たせる。送信者は認可された接続から特定し、本文のユーザーIDをそのまま信用しない。受信側は同じ適用処理を通す。

| データ | 最初に採用する扱い |
| --- | --- |
| チャット | 一意なIDで追加。表示順は同時送信でも一致する規則を定義する |
| キャンバス | 線ごとのIDで追加・削除。削除済みIDを保持し、遅れて来た追加による復活を防ぐ |
| サイコロ | 振ったクライアントが結果を確定し、その結果をイベントとして配る |
| アイテムの操作 | サーバーが操作権と世代を割り当てる。同じ対象への更新は権利を持つ人から採用する |
| 全体設定・競合するゲーム操作 | 競合規則を定義するまではサーバーで順序を確定する |

同じ送信者からの配送順序だけでは、複数人が送った更新の全体順序は揃わない。順序によらず同じ結果になる操作、単独の操作権、サーバーでの順序確定を用途ごとに選ぶ。

声の範囲のチャット、シークレットのサイコロなどは宛先の認可と機密性を維持する。位置用の共有鍵を流用せず、許可された受信者だけが復号できる形にする。

## 初回同期と保存

最初はサーバーがスナップショットを返す。P2Pで発生した更新も、保存や復元に必要な範囲でサーバーへ確実配送する。クライアントで見えた更新とサーバーで保存済みの更新は区別する。

スナップショットには取り込み済みのイベント範囲を付ける。取得中の更新をバッファし、スナップショット適用後に未取り込み分だけを適用する。欠落や履歴保持上限を検出したら、新しいスナップショットからやり直す。削除済みIDや操作権の世代も復元対象に含める。

将来、同じ受け渡し手順を使って他のpeerからスナップショットを取得できるようにする。初期段階ではpeerによる初回同期やホスト選挙を導入しない。

## 実装順と確認条件

1. kokosyncにpeer間の確実配送・大容量転送を追加する。既存のAPIと混在できるよう、通信の種類ごとの対応能力を通知する。
2. Tonariumに共通のイベント適用処理を用意する。まずチャットとサイコロを移し、キャンバス、アイテム操作へ広げる。
3. 初回同期中の更新、再接続、保存、権限付きの宛先を確認する。未対応の組は従来のサーバー経由に戻す。
4. ブラウザ5人と直結できないクライアントの混在で検証する。通信断・途中での経路変更・重複・順序入れ替わり・退出・大容量転送中にも、更新の欠落や二重適用がなく、失敗時は再同期できることを確認する。

まずkokosync側の配送契約を固める。Tonarium側で独自の再送・分割・経路切り替えを重ねて実装しない。

## kokosync更新の確認結果（2026-10-21）

対象は `b55ed5d0ad5beb7f64161d904294b40fc442f69b`。`sendTo(peer, topic, value)`、`peer_message`、`deliveryStats()`が追加され、上記の確実配送と大容量転送を実装している。既存のmessage履歴は別のまま。JSのP2Pは専用の順序付き・再送ありDataChannelを使い、直結できない相手は同じ契約で中継する。

デプロイ後の `https://45.77.130.146` で `peerDelivery.version: 1` を確認した。公開先の `index.js`・`routing.js`・`peer-delivery.js` は対象コミットのローカルファイルとハッシュが一致した。

今回実行した確認:

- JSのpeer配送・routing・fragmentationテスト38件が成功。受信確認の欠落、重複、順序逆転、直結から中継への切り替え、容量上限、接続世代を含む。
- Goの `go test ./...` が成功。
- C#の基礎・fragmentation・routing・peer配送テストと、ローカルWebSocketによる150,000バイトの双方向配送テストが成功。
- JSのローカル実接続テストで1 MiB、トピックごとの順序、返信、キャンセル、同名での再参加を確認。
- 公開先に5つのNodeクライアントを接続。1人から他の4人へ、それぞれ1 MiBと小さい操作を並行送信し、全件の受信確認とハッシュ一致を確認。小さい操作は全受信者で大容量データより先に届き、コアの履歴連番は増えなかった。今回の公開先テストはWebSocket中継経路。ブラウザ直結の実機検証はkokosync側の `docs/peer-delivery-validation.md` に記録されている。

取り込み時の注意:

- Tonarium同梱SDKを新しい実行モジュール一式と型定義へ更新済み。Tonarium独自のoffer・WebSocketプロキシと接続タイムアウトの指定を維持している。
- 公開先の既定値は1値4 MiB、送受信予算各8 MiB、同時転送4、保持する配送列64。大容量値は受信完了までメモリに保持する方式で、無制限のストリームAPIではない。全員への送信は相手ごとの独立したコピーになるため、合計待機量を管理する。
- 配送列は送信者・相手・接続世代・トピックごと。同じトピックでは一度に1件だけ受信確認を待つ。用途ごとの少数の固定トピックを使い、アイテムIDごとにトピックを増やさない。頻繁な描画点はまとめて送ることも検討する。
- スナップショットと操作は別トピックにする。非同期の適用順序、イベントID、保存確認、途中参加との整合はTonariumで実装する。
- 送信開始後に配送列が失敗すると、後続は `LaneFailed` になる。自動的に別イベントとして再送せず、新しい接続世代で再同期する。
