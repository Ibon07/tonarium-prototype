# 同期受信の切断を防ぐ回帰試験

同期の受信をUI処理から分離した。位置は同じユーザーの最新値へ集約し、チャット・操作・Snapshot/Blobは受信順を守る。SDKのイベント容量16件は変更していない。

## 再現で分かったこと

2026-10-21の既存ログには、13:20:39と14:07:42に `Event consumer queue overflow` が残っていた。ただし、当時のイベント到着時刻やUI処理時間は記録されておらず、どの画面処理が発火点だったかは断定できない。

そこで、別プロセスのJSクライアントから実際のローカルTonariumへ位置150件・チャット12件・付箋編集12件を送り、受信するネイティブ側のUIスレッドを2.2秒止めた。修正前は1.9秒の送信中にUI反映待ちが2,174msとなり、SDKキューの17件目の `latest` で切断した。この時点のキューは5,682バイトで、バイト上限ではなく件数上限への到達だった。記録は [evidence/before.json](evidence/before.json)。

この再現は、受信ループがUIを待つ設計だけで同じ例外を起こせることを示す。歴史的な2回の障害がすべて同じUI処理から始まったことまでは示さない。

## 受信と反映の役割

`TonariumClient` の1接続は、受信処理、順序を保持する受信バッファ、UI反映処理を所有する。

- 受信処理はSDKのイベントを取り出し、送信元・暗号・連番を検証する。UI反映は待たない。
- 位置は未反映の同一ユーザーの値にまとめる。ただし確実配送のメッセージを挟んで集約しない。Snapshotや退出より前の位置が、それらの後へ移動するのを防ぐ。
- チャット・操作・Snapshotは順序付きのスロットに置く。Blobも受信開始時にスロットを確保する。転送とハッシュ検証は受信処理と並行して進み、後続の確実配送はそのスロットを追い越さない。
- UIへは最大32件を一括で渡す。個々の `MessageReceived` は維持し、画面更新の `State.Touch` は一括反映後に1回だけ呼ぶ。同時に待機するUI反映は1つ。
- バッファは処理中のデータも含めて256件・暗号化ペイロード64MiBまで。超過時は接続を閉じ、画面へ通知してSnapshotを取り直す。メッセージを黙って捨てたまま処理を続けない。32MiBの単一パケット上限も維持する。
- 再接続・退出で世代とキャンセルを更新する。UIコールバック内でも世代を確認する。旧世代の受信とBlobの終了を待ち、送信も世代とキャンセルで無効化する。古い資格で新しい部屋へ反映しない。

SDK側の変更は、到着件数・取り出し件数・ピーク件数とバイト数・取り出しまでの時間・あふれたイベント種類を記録する診断だけ。容量、配送、フロー制御の仕様は変えていない。アプリ側はUI待ち・UI適用時間・復号時間・Blob待ちと、集約件数を公開する。ペイロードや認証鍵は診断に出さない。

## 検証を再実行する

リポジトリ直下で実行する。`.env` のKokoSync設定を使うため、到達可能なKokoSyncが必要。Tonariumのデータは `native/artifacts/sync-receive/server-data` に隔離される。以下のサーバーとプロキシは別のターミナルで起動する。ポートを他の作業が使っていないことを先に確認する。

```powershell
node native/Tonarium.SyncSmoke/server.cjs
```

```powershell
node native/Tonarium.SyncSmoke/delay-proxy.cjs 31327 http://localhost:3027 10
```

```powershell
$dotnet = "$env:LOCALAPPDATA/Tonarium/dotnet/dotnet.exe"
& $dotnet run --project native/Tonarium.SyncSmoke -c Release -- `
  http://127.0.0.1:31327 native/artifacts/sync-receive/result.json `
  http://localhost:3027 --drop-sync --saturate
```

プロキシは各方向に10ms遅延を入れる。`/__drop-sync` はこのプロキシに接続した同期ソケットだけを強制終了し、ホーム接続を残す試験用エンドポイント。共有・公開のサーバーとして使わない。

試験は順に、UI停止中の位置集中と確実配送、1.5MBの添付と後続編集、1800本の線を持つSnapshot中の位置受信、実接続の切断と自動復旧、8秒のUI停止中に300操作を送り上限を超えた場合の復旧、旧世代のUI反映防止、Blob途中の退出と別部屋への参加を確認する。添付データはサイズと配送確認用で、画像としての描画は対象外。

JS送信者は受信側と別プロセスなので、受信側のUI停止で送信まで止まることはない。位置は最終値、チャットは全12件の順序と重複なし、操作は最終値、Snapshotは添付と編集結果の一致を判定する。過負荷時は通知を確認したうえで、最後の `limit-299` まで復元されることを確認する。

サーバーはチャットをメモリに保持する。繰り返すとSnapshotに試験用の添付が蓄積するため、同条件で比較する際はサーバーを再起動する。

## 修正後の計測結果

最終試験の記録は [evidence/after.json](evidence/after.json)。通常の集中負荷では例外は0件で、UI待ち中もSDKから取り出し続けた。

| 計測項目 | 修正前 | 修正後の最終試験 |
| --- | ---: | ---: |
| 集中負荷の送信時間 | 1,905ms | 1,880ms |
| SDKの最大件数（入れようとした件数を含む） | 17件で切断 | 3件 |
| UI反映待ちを含む最大待ち | 2,174ms | 2,166ms |
| 集約した位置 | なし | 137件 |
| アプリ側の最大保持件数 | なし | 37件 |

後半の大きいSnapshotでは、Blob完了待ちの間に位置289件を受信し、SDKキューの最大は3件だった。上限試験ではアプリ側の保持が256件に達して再同期し、最後の編集まで復元した。Blob途中の退出から別部屋の同期完了までは201msだった。

試験を繰り返した最終実行では、前の試験の添付がSnapshotに残っている。集中負荷の比較に使う位置・チャット・操作の件数は同じだが、初期Snapshotの容量と所要時間を修正前後の速度比較には使わない。SDKの滞留時間は取り出せたイベントだけを計測し、あふれた際に破棄された未処理イベントは含まない。

## 既存の回帰試験

`Tonarium.Smoke` の全通常経路は成功。2つのネイティブとJS SDKの間で、暗号化Snapshot、位置、チャット、付箋、キャンバス差分と全消去、再参加時の一致、大きい画像、ワールド変更、フレンド、DMを確認した。

`Tonarium.UiSmoke --canvas-sync` も成功。実際のポインター入力104点を21回の追加メッセージへまとめ、全点の順序一致、単一点、指を離した直後の送信を確認した。入力終了から受信完了までは約21msだった。記録は [evidence/ui-canvas.json](evidence/ui-canvas.json)。

`Tonarium.UiSmoke --menu` の全通常経路も、設定を隔離して成功。ログイン、ホーム、セッション参加、チャット、付箋の編集と相手への反映、DM、各メニュー、最小画面・150% DPI、退出を確認した。最初の実行では保存済み名前によって接続先欄が折り畳まれ、ログイン前の入力テストで停止した。共有のテスト起動コードは編集せず、一時ランチャーから `DesktopInstance.Acquire` に専用ディレクトリを渡して再実行した。

## 適用範囲と残る制限

検証はWindows上のReleaseビルド、ローカルTonarium、設定済みKokoSync、遅延付きWebSocketで実施した。UIの描画検証はHeadless/Skiaであり、Unityの実描画や物理的なウィンドウ操作を保証するものではない。3D終了処理・アバター描画の変更は別作業の担当範囲。

極端な確実配送の集中では上限に達し、再同期する。過負荷を無制限に保持する設計ではない。再同期はサーバーの現在状態を復元するが、一過性の通知をすべて再演する保証はない。64MiBは暗号化ペイロードの予算であり、JSONオブジェクト等を含むプロセス全体のメモリ上限ではない。

既存配布ZIP・インストール済み実行ファイルは更新していない。修正は開発版と配布版が共用するソースに入り、DesktopのReleaseビルドで確認した。配布へ反映する際は、ほかの並行修正と合わせて再ビルドする。
